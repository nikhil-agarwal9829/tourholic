# Build Touroholic — A Complete Tour Discovery and Booking Platform

Act as a senior full-stack developer, database architect, UI/UX designer, and software tester. Build a complete, polished, responsive tour discovery and booking web application called **Touroholic**.

This is a redevelopment of a tour management application inspired by Natours. The main focus is excellent UI/UX, proper MongoDB schema design, realistic booking workflows, authentication, and practical recommendation features.

Do not create only a static frontend or a prototype. Build a functional full-stack application with a clear architecture, reusable components, database models, API routes, validation, error handling, and deployment readiness.

## 1. Technology stack

Use the following stack:

- **Framework:** Next.js with App Router
- **Language:** TypeScript with strict type checking
- **Frontend:** React
- **Styling:** Tailwind CSS
- **UI components:** shadcn/ui
- **Icons:** Lucide React
- **Backend:** Next.js Route Handlers under `app/api/`
- **Database:** MongoDB Atlas
- **ODM:** Mongoose
- **Authentication:** Auth.js or a secure credentials-based authentication implementation
- **Form validation:** Zod and React Hook Form
- **Image hosting:** Configurable image provider, preferably Cloudinary
- **Deployment:** Vercel
- **Testing:** Vitest or Jest for unit tests and Playwright for important end-to-end workflows

Use compatible, stable package versions. Avoid unnecessary dependencies and keep the project compatible with Vercel's standard Next.js deployment.

Do not create a separate Express server unless there is a compelling technical reason. Keep the application and API in one Next.js repository for simpler deployment.

Create a premium travel-booking website with an elegant, modern, image-rich interface.

Avoid generic dashboard-like designs, excessive gradients, excessive glassmorphism, cluttered layouts, and oversized decorative elements.

Create a consistent design system with reusable buttons, inputs, cards, badges, dialogs, navigation, skeleton loaders, and toast notifications.

Build a complete tour discovery page.

Features:

### E. User profile — `/profile`

### F. Booking flow — `/checkout` and `/my-bookings`

Implement a realistic booking workflow.

Steps:

1. User selects a tour.
2. User selects a valid departure date and traveler count.
3. The application checks availability and calculates the price on the server.
4. User reviews the booking summary.
5. User confirms the reservation.
6. The backend validates availability again and creates the booking.
7. The user sees a confirmation page with a booking reference.
8. The booking appears in My Bookings.

Use MongoDB transactions where supported for inventory-sensitive operations, with an appropriate fallback or atomic update strategy when transactions are unavailable.

Prevent duplicate submissions, invalid quantities, price tampering, unauthorized booking access, and overbooking.

For this initial version, implement a clear booking status lifecycle such as `pending`, `confirmed`, `cancelled`, and `completed`, plus payment statuses such as `unpaid`, `paid`, `failed`, and `refunded`.

Do not mark a booking as paid without a verified payment confirmation. If a payment provider is not configured, support an explicitly labelled demo or unpaid reservation workflow rather than pretending a payment succeeded.

Add cancellation rules and validate them on the server.

### G. Reviews

Allow authenticated users to submit a rating and written review.

Requirements:
- Rating from 1 to 5.
- Review text validation.
- One review per user per tour.
- Edit and delete the user's own review.
- Display review author, rating, date, and text.
- Recalculate the tour's average rating and rating count consistently.
- Enforce the one-review rule using a unique compound MongoDB index.

### H. Admin dashboard — `/admin`

Create role-protected admin pages for:

- Dashboard statistics.
- Create, edit, and delete tours.
- Upload or select tour images.
- Manage tour schedules and capacity.
- View and manage bookings.
- Manage users and roles.
- Moderate reviews.

Use server-side authorization for every administrative operation. Hiding an admin button in the frontend is not sufficient security.

## 4. MongoDB database design

Design proper Mongoose schemas before implementing the business logic.

Create the following collections.

### A. Users

Suggested fields:

- `_id`
- `name`
- `email`
- `passwordHash`
- `photo`
- `role`: `user` or `admin`
- `active`
- `favoriteTours`: array of Tour ObjectIds, or a separate favourites collection if more suitable
- `createdAt`
- `updatedAt`

Requirements:
- Normalize email values.
- Enforce unique email addresses.
- Never return password hashes through public API responses.
- Validate all fields.

### B. Tours

Suggested fields:

- `_id`
- `name`
- `slug`
- `summary`
- `description`
- `category`
- `duration`
- `maxGroupSize`
- `difficulty`
- `price`
- `currency`
- `ratingsAverage`
- `ratingsQuantity`
- `imageCover`
- `images`: array of image URLs and optional metadata
- `startLocation`: GeoJSON Point with longitude and latitude
- `locations`: array of GeoJSON-based or structured locations
- `guides`: references to users with appropriate guide information
- `itinerary`: array of day number, title, and description
- `included`
- `excluded`
- `highlights`
- `cancellationPolicy`
- `isPublished`
- `createdAt`
- `updatedAt`

Create a unique index on `slug`, suitable indexes for commonly used filters, and a `2dsphere` index for `startLocation`.

Do not create indexes indiscriminately. Document which query each important index supports.

### C. Reviews

Fields:

- `_id`
- `tour`: Tour ObjectId
- `user`: User ObjectId
- `rating`
- `review`
- `createdAt`
- `updatedAt`

Create a unique compound index on `{ tour: 1, user: 1 }`.

### D. Bookings

Fields:

- `_id`
- `bookingReference`
- `user`: User ObjectId
- `tour`: Tour ObjectId
- `departureDate`
- `travelers`
- `pricePerTraveler`
- `totalPrice`
- `currency`
- `bookingStatus`
- `paymentStatus`
- `paymentReference`, when applicable
- `createdAt`
- `updatedAt`

Store the agreed booking price as a historical snapshot. Do not rely only on the current tour price to display past bookings.

### E. Tour schedules / departures

Create a separate `TourDeparture` or `TourSchedule` collection because departures have their own availability and capacity.

Suggested fields:
- `_id`
- `tour`: Tour ObjectId
- `startDate`
- `endDate`
- `capacity`
- `reservedSeats`
- `status`
- `createdAt`
- `updatedAt`

Validate `reservedSeats` against capacity and prevent concurrent requests from overselling the remaining seats.

### F. Optional favourites

If favourites need their own collection, use:

- `_id`
- `user`: User ObjectId
- `tour`: Tour ObjectId
- `createdAt`

Create a unique compound index on `{ user: 1, tour: 1 }`.

Explain your embedding-versus-referencing decisions in the README.

## 7. Recommendation system — no LLM required

Build a basic, explainable rule-based recommendation engine.

Inputs can include:
- Preferred destination.
- Budget.
- Preferred difficulty.
- Tour category.
- Duration.
- Previous bookings.
- Favourite tours.
- Previously reviewed tours.

Ranking approach:
1. Match the user's budget.
2. Prioritize preferred categories and destinations.
3. Consider duration and difficulty preferences.
4. Boost relevant ratings and popularity.
5. Exclude unpublished tours and, where departure dates matter, tours without eligible availability.

Return a ranked list with short explanations such as:
- "Matches your budget."
- "Similar to tours you saved."
- "Highly rated adventure tour."
- "Matches your preferred duration."

Do not describe this as machine learning or AI if it is a rule-based scoring algorithm.

For logged-out users, provide general recommendations based on popular, highly rated, or featured tours.

Keep the scoring function separate and testable.
